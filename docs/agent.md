# AGENT.md --- دستورالعمل ساخت موزیک‌پلیر دسکتاپ

## 1. مأموریت پروژه

یک موزیک‌پلیر دسکتاپ مدرن، سریع، پایدار و بسیار زیبا بساز. محصول باید حس
یک نرم‌افزار پریمیوم و دقیق را منتقل کند؛ نه یک داشبورد اداری و نه صرفاً
مجموعه‌ای از کامپوننت‌های آماده. ظاهر، تجربه شنیدن موسیقی، سرعت تعامل،
مدیریت کتابخانه و کیفیت جزئیات در اولویت‌اند.

**اصل کلیدی:** ابتدا تجربه کاربری و معماری را درست طراحی کن؛ سپس
قابلیت‌ها را مرحله‌به‌مرحله پیاده‌سازی کن. از ساخت قابلیت‌های نمایشیِ
غیرعملیاتی یا دکمه‌هایی که واقعاً کاری انجام نمی‌دهند خودداری کن.

## 2. فناوری‌های تعیین‌شده

فناوری‌های اصلی پروژه ثابت هستند و بدون دلیل فنی روشن تغییر نکنند:

-   **زبان:** TypeScript در تمام بخش‌های ممکن؛ از `any` بی‌دلیل استفاده
    نکن.
-   **Runtime و package manager:** Bun.
-   **Backend/API:** ElysiaJS روی Bun.
-   **Database:** PostgreSQL.
-   **ORM و اعتبارسنجی:** Prisma برای دسترسی به دیتابیس و Zod برای
    اعتبارسنجی ورودی‌ها، مگر اینکه مخزن موجود از قبل تصمیم سازگار دیگری
    داشته باشد.
-   **Desktop shell:** ElectronJS.
-   **Frontend:** Vue 3 با Composition API و `<script setup lang="ts">`.
-   **UI:** shadcn-vue و Tailwind CSS؛ کامپوننت‌ها را مطابق سیستم طراحی
    پروژه شخصی‌سازی کن.
-   **State:** Pinia برای state سراسریِ واقعاً لازم.
-   **Routing:** Vue Router.
-   **Testing:** Vitest برای منطق و کامپوننت‌ها؛ Playwright یا ابزار
    سازگار برای تست جریان‌های اصلی Electron، در صورت امکان.
-   **API contract:** قرارداد TypeScript مشترک و اعتبارسنجی ورودی/خروجی
    روشن میان کلاینت و سرور.

پیش از نصب یا به‌روزرسانی پکیج‌ها، نسخه‌های موجود و سازگاری آن‌ها را بررسی
کن. از ایجاد چند ابزار هم‌پوشان برای یک مسئولیت خودداری کن.

## 3. معماری و ساختار

معماری باید **Modular Monolith** باشد؛ ماژولار و قابل توسعه، بدون تقسیم
زودهنگام به microservice. مرزهای ماژول‌ها واضح باشند و هر ماژول مالک منطق
و داده‌های حوزه خودش باشد.

ساختار پیشنهادی، متناسب با مخزن موجود قابل تطبیق است:

``` text
apps/
  desktop/
    electron/
      main/
      preload/
    renderer/
      src/
        app/
        components/
        features/
        layouts/
        pages/
        router/
        stores/
        styles/
        lib/
  api/
    src/
      modules/
        library/
        playback/
        playlists/
        search/
        metadata/
        settings/
        artwork/
        statistics/
      plugins/
      shared/
packages/
  contracts/
  config/
  ui/                  # فقط در صورت نیاز واقعی به اشتراک‌گذاری
prisma/
  schema.prisma
  migrations/
tests/
docs/
```

قواعد معماری:

1.  Electron Main، Preload، Renderer و Backend مرزهای امنیتی و
    مسئولیت‌های جدا دارند.
2.  Renderer نباید دسترسی مستقیم به Node.js یا فایل‌سیستم داشته باشد؛
    ارتباط فقط از طریق API محدود و تایپ‌شده‌ی Preload/IPC باشد.
3.  تمام کانال‌های IPC باید allowlist، اعتبارسنجی ورودی و خروجی، و
    نام‌گذاری منظم داشته باشند.
4.  منطق دامنه را داخل Vue component، handlerهای IPC یا route handlerهای
    حجیم ننویس.
5.  مسیرهای API باریک باشند؛ منطق کسب‌وکار در service/use-case و دسترسی
    به داده در repository یا لایه داده قرار گیرد.
6.  ماژول‌ها تا حد ممکن مستقل باشند و به جزئیات داخلی یکدیگر دسترسی
    مستقیم نداشته باشند.
7.  وابستگی‌های دوری را حذف کن. وابستگی‌ها باید جهت مشخص داشته باشند.
8.  برای قابلیت‌های جدید، اول ماژول و قرارداد آن را مشخص کن؛ سپس
    پیاده‌سازی را انجام بده.
9.  از abstraction و الگوهای پیچیده‌ای که هنوز نیاز واقعی ندارند پرهیز
    کن.
10. نام‌گذاری فایل‌ها، کلاس‌ها، توابع، eventها و APIها در کل پروژه یکدست
    باشد.

## 4. محدوده محصول و قابلیت‌های پلیر

قابلیت‌ها را به‌صورت مرحله‌ای پیاده‌سازی کن. اولویت، تجربه‌ی محلیِ پایدار و
سریع است.

### 4.1 پخش موسیقی

-   پخش، توقف، ادامه، آهنگ قبلی و بعدی.
-   نوار پیشرفت با زمان فعلی و مدت کل؛ امکان seek دقیق.
-   کنترل صدا، mute و نمایش وضعیت واضح.
-   حالت‌های Shuffle و Repeat: خاموش، تکرار آهنگ، تکرار صف.
-   صف پخش قابل مشاهده و قابل مدیریت؛ افزودن، حذف، جابه‌جایی و پاک‌کردن
    آیتم‌ها.
-   حفظ موقعیت پخش و صف، با رعایت تنظیمات کاربر.
-   پشتیبانی از فرمت‌های متداولی که Chromium/Electron واقعاً پشتیبانی
    می‌کند؛ فرمت‌ها را بدون تست ادعا نکن.
-   مدیریت فایل خراب، فرمت ناشناخته، فایل حذف‌شده و خطای decode با پیام
    قابل فهم.
-   جلوگیری از پخش هم‌زمان ناخواسته چند آهنگ.
-   نمایش حالت‌های loading، buffering، paused، playing و error.
-   رفتار مناسب در زمان تغییر آهنگ، seek سریع و کلیک متوالی روی کنترل‌ها.

### 4.2 کتابخانه موسیقی

-   انتخاب یک یا چند پوشه موسیقی توسط کاربر.
-   اسکن اولیه و به‌روزرسانی کتابخانه؛ امکان اسکن مجدد.
-   نمایش آهنگ‌ها با عنوان، هنرمند، آلبوم، مدت، شماره ترک و مسیر/منبع در
    صورت نیاز.
-   مرتب‌سازی و فیلتر بر اساس فیلدهای موجود.
-   تشخیص تکراری‌ها با رویکرد قابل توضیح؛ صرفاً به نام فایل اکتفا نکن.
-   پشتیبانی از فایل‌های بدون metadata و نمایش fallback مناسب.
-   نمایش خطاهای اسکن و امکان تلاش مجدد.
-   برای کتابخانه بزرگ از pagination، virtualization و پردازش دسته‌ای
    استفاده کن.
-   اسکن سنگین نباید UI را مسدود کند؛ پیشرفت اسکن را نمایش بده.

### 4.3 صفحات و مجموعه‌ها

-   Home / Recently Played.
-   All Songs.
-   Albums.
-   Artists.
-   Playlists.
-   Favorites / Liked Songs.
-   Queue / Now Playing.
-   Search.
-   Settings.
-   Playlistها باید امکان ایجاد، تغییر نام، حذف، مرتب‌سازی و افزودن/حذف
    آهنگ داشته باشند.
-   علاقه‌مندی‌ها و تاریخچه پخش باید پایدار باشند.
-   برای داده‌های خالی، صفحه خالی زیبا و راهنمای اقدام بعدی طراحی کن.

### 4.4 جست‌وجو و metadata

-   جست‌وجوی سریع در عنوان، هنرمند، آلبوم و نام فایل.
-   debounce برای ورودی جست‌وجو در صورت نیاز.
-   نرمال‌سازی مناسب حروف و فاصله‌ها، به‌ویژه برای فارسی و انگلیسی.
-   خواندن metadata از فایل‌ها در صورت امکان و ثبت نتیجه در دیتابیس.
-   امکان اصلاح metadata فقط در صورتی که نوشتن در فایل به‌طور ایمن و
    آگاهانه پیاده‌سازی شده باشد؛ تغییر فایل اصلی بدون تأیید کاربر ممنوع.
-   برای کاور آلبوم، ابتدا از metadata داخلی فایل استفاده کن؛ نبود کاور
    باید fallback جذاب داشته باشد.
-   هیچ سرویس آنلاین، scraping یا ارسال فایل/اطلاعات کاربر به سرویس ثالث
    را بدون رضایت روشن اضافه نکن.

### 4.5 تجربه سیستم‌عامل

-   کنترل‌های media key و multimedia keyboard در صورت پشتیبانی و تست.
-   نمایش اطلاعات آهنگ در قابلیت‌های رسانه‌ای سیستم‌عامل، در صورت امکان.
-   پشتیبانی از minimize، maximize، close و رفتار پنجره قابل پیش‌بینی.
-   حفظ وضعیت و تنظیمات پس از restart.
-   تنظیم رفتار هنگام بستن پنجره، tray و اجرای مجدد را شفاف طراحی کن؛
    هیچ رفتار پنهانی نداشته باش.
-   به‌روزرسانی برنامه و نصب‌کننده فقط با تصمیم و پیکربندی صریح پروژه؛ از
    به‌روزرسانی خودکار ناخواسته اجتناب کن.

### 4.6 قابلیت‌های تکمیلی، پس از تثبیت هسته

-   Equalizer با presetهای قابل انتخاب، فقط در صورت وجود پیاده‌سازی صوتی
    واقعی و تست‌شده.
-   Crossfade، gapless playback یا ReplayGain فقط پس از بررسی فنی و تست
    عملی؛ وجود دکمه بدون اثر واقعی پذیرفته نیست.
-   نمایش waveform یا visualizer فقط اگر هزینه عملکردی آن کنترل شده
    باشد.
-   Lyrics فقط با منبع مجاز و با رعایت حق نشر و حریم خصوصی.
-   آمار شنیدن، بیشترین پخش‌شده‌ها و اخیراً پخش‌شده‌ها.
-   تم روشن/تاریک و تنظیمات دسترس‌پذیری.
-   در صورت نیاز به همگام‌سازی یا حساب کاربری، آن را یک فاز مستقل بدان؛
    نسخه اولیه باید بدون وابستگی به حساب آنلاین قابل استفاده باشد.

## 5. الزامات طراحی بصری --- اولویت بسیار بالا

هدف، ساخت رابطی **استثنایی، لوکس، مینیمال و موسیقی‌محور** است. رابط نباید
شبیه قالب پیش‌فرض shadcn یا داشبوردهای مدیریتی به نظر برسد.

### اصول طراحی

-   پیش از کدنویسی، design system کوچک اما کامل تعریف کن: رنگ‌ها،
    تایپوگرافی، spacing، radius، سایه‌ها، borderها، آیکون‌ها و حالت‌های
    تعاملی.
-   از یک زبان بصری منسجم استفاده کن؛ هر صفحه نباید سبک متفاوتی داشته
    باشد.
-   فضای خالی هدفمند، سلسله‌مراتب بصری قوی، ترکیب‌بندی متعادل و جزئیات
    ظریف داشته باش.
-   رنگ‌های اصلی و accent محدود باشند؛ از رنگ‌های نئونی متعدد، gradientهای
    تصادفی و glow افراطی دوری کن.
-   رنگ‌ها را با CSS variables و design tokens تعریف کن تا تغییر تم آسان
    باشد.
-   کاور آلبوم، تایپوگرافی، فضای اطراف کنترل‌های پخش و ناحیه Now Playing
    باید مرکز توجه باشند.
-   برای اطلاعات کم‌اهمیت از متن کم‌رنگ‌تر استفاده کن، اما کنتراست و
    خوانایی را فدای زیبایی نکن.
-   آیکون‌ها از یک مجموعه و با اندازه و stroke سازگار انتخاب شوند؛ از
    emoji به‌عنوان آیکون رابط استفاده نکن.
-   انیمیشن‌ها کوتاه، نرم و معنادار باشند؛ برای `prefers-reduced-motion`
    احترام قائل شو.
-   hover، focus، pressed، selected، disabled، loading و empty stateها
    همگی طراحی شوند.
-   skeleton فقط جایی استفاده شود که واقعاً loading وجود دارد.
-   طراحی باید در اندازه‌های مختلف پنجره Electron سازگار بماند؛ هیچ
    صفحه‌ای نباید با resize بشکند.
-   از متن‌های نمونه بی‌معنا، کاورهای تصادفی دائمی و داده‌های ساختگی در
    محصول نهایی استفاده نکن.
-   اگر کتابخانه خالی است، به‌جای صفحه‌ی خالیِ بی‌روح، یک onboarding زیبا
    برای انتخاب پوشه ارائه کن.

### جهت هنری پیشنهادی

یک رابط دسکتاپ با حس محصول premium: پس‌زمینه عمیق و آرام، سطح‌بندی دقیق،
تایپوگرافی با شخصیت، کاورهای بزرگ و باکیفیت، جزئیات کم اما حساب‌شده و
نوار پخش ثابت در پایین. این جهت هنری نقطه شروع است؛ آن را با نمونه‌های
واقعی درون پروژه اصلاح کن، نه با افزودن افکت‌های بی‌هدف.

### چیدمان پیشنهادی

-   **Sidebar:** لوگو/نام محصول، کتابخانه، مجموعه‌ها و playlistها.
-   **Main content:** صفحه جاری با عنوان واضح، جست‌وجو، فیلتر و grid/list
    مناسب.
-   **Now Playing bar:** کاور کوچک، عنوان/هنرمند، کنترل‌ها، seek bar و
    صدا؛ در پنجره‌های کوچک فشرده شود.
-   **Now Playing view:** کاور بزرگ، اطلاعات آهنگ، کنترل‌ها و پس‌زمینه
    هماهنگ با artwork؛ خوانایی همیشه حفظ شود.
-   **Queue panel:** پنل جانبی یا drawer قابل باز و بسته شدن با مدیریت
    صف.
-   **Context menus:** برای آهنگ‌ها و playlistها با گزینه‌های مرتبط و قابل
    دسترس.

این چیدمان را کورکورانه تحمیل نکن؛ با prototype و تست کاربردپذیری اصلاحش
کن.

### کیفیت اجرا

-   هیچ دکمه‌ای صرفاً تزئینی نباشد.
-   از layout shift، پرش کاور، کنترل‌های جابه‌جا‌شونده و اسکرول‌های تو در
    توی غیرضروری جلوگیری کن.
-   برای فهرست آهنگ‌ها، hover و selected state ظریف اما واضح داشته باش.
-   کاورهای مفقود باید placeholderهای خوش‌ساخت و سازگار با طراحی داشته
    باشند.
-   خطاها با زبان ساده، علت قابل فهم و اقدام پیشنهادی نمایش داده شوند.
-   ظاهر زیبا باید در داده واقعی و طولانی نیز حفظ شود، نه فقط در
    screenshot نمایشی.

## 6. پخش صدا و مدیریت فایل

-   ابتدا مشخص کن پخش صدا در Renderer انجام می‌شود یا لایه دیگری لازم
    است؛ برای هر انتخاب دلیل فنی و محدودیت‌ها را مستند کن.
-   پخش فایل محلی باید با API امن و سازگار با Electron پیاده‌سازی شود؛
    مسیرهای محلی را بی‌محابا در URL یا IPC قرار نده.
-   برای انتخاب پوشه/فایل از dialog امن Electron استفاده کن.
-   مسیرها را در سرور یا Renderer از ورودی غیرقابل اعتماد مستقیم اجرا
    نکن.
-   از خواندن کل فایل صوتی در حافظه خودداری کن؛ در صورت امکان از stream
    یا قابلیت مناسب پلتفرم استفاده کن.
-   برای کتابخانه‌های حجیم، metadata و artwork را با cache کنترل‌شده
    مدیریت کن.
-   اگر artwork cache روی دیسک ذخیره می‌شود، مسیر و اندازه cache را کنترل
    کن و امکان پاک‌سازی آن را فراهم کن.
-   تغییر نام، جابه‌جایی یا حذف فایل در سیستم کاربر نباید بدون اقدام صریح
    کاربر انجام شود.

## 7. نقش PostgreSQL و داده‌ها

PostgreSQL باید برای داده‌های پایدار و ساختاریافته استفاده شود؛ نه
به‌عنوان جایگزین فایل‌سیستم برای ذخیره باینری فایل‌های موسیقی.

مدل‌های اولیه را با نیاز واقعی هماهنگ کن؛ حداقل موجودیت‌های احتمالی:

-   Track
-   Artist
-   Album
-   Playlist
-   PlaylistTrack (با ترتیب آیتم‌ها)
-   Favorite یا فیلد/رابط مناسب برای علاقه‌مندی
-   PlayHistory
-   LibraryFolder
-   AppSettings

قواعد داده:

1.  کلیدها، unique constraintها، foreign keyها و رفتار حذف را دقیق تعریف
    کن.
2.  برای queryهای پرتکرار index مناسب بساز؛ قبل از افزودن index، query
    pattern را بررسی کن.
3.  مدت زمان، ترتیب ترک و زمان‌ها را با نوع داده مناسب ذخیره کن.
4.  مسیر فایل را به‌عنوان شناسه پایدار فرض نکن؛ فایل ممکن است جابه‌جا یا
    rename شود.
5.  اسکن مجدد باید idempotent باشد و رکوردهای تکراری ناخواسته نسازد.
6.  migrationها نسخه‌بندی‌شده باشند و تغییر schema دستی و بی‌ردیابی ممنوع
    باشد.
7.  ورودی‌ها در مرز API اعتبارسنجی شوند و خطاهای دیتابیس به پیام امن و
    قابل فهم تبدیل شوند.
8.  تراکنش را برای عملیات چندمرحله‌ای لازم به‌کار ببر.
9.  داده‌های تاریخچه و آمار باید مطابق تنظیمات و سیاست نگهداری مشخص رفتار
    کنند.
10. رمز عبور، token یا secret در کد، log، دیتابیس بدون ضرورت یا فایل
    قابل انتشار ذخیره نشود.

**تصمیم معماری مهم:** مشخص کن PostgreSQL کجا اجرا می‌شود. برای یک پلیر
دسکتاپ آفلاین، اجبار کاربر به نصب یا اتصال به PostgreSQL محلی ممکن است
تجربه نصب را دشوار کند. پیش از پیاده‌سازی، یک ADR کوتاه بنویس و یکی از
این دو مدل را با دلیل انتخاب کن: - PostgreSQL روی سرور/شبکه و اپلیکیشن
به‌عنوان client؛ یا - PostgreSQL محلیِ مدیریت‌شده با روش نصب، اجرا، backup،
ارتقا و بازیابی روشن.

اگر هدف محصول، پلیر شخصیِ آفلاین و نصب آسان است، این محدودیت را صریح
گزارش کن و بدون اجازه، دیتابیس دیگری را جایگزین PostgreSQL نکن. برای
اتصال دسکتاپ به API راه دور نیز احراز هویت، مجوزها و امنیت ارتباط را
طراحی کن.

## 8. Backend با ElysiaJS

-   routeها را بر اساس ماژول دامنه سازمان‌دهی کن.
-   از schemaهای Elysia/Zod مطابق الگوی انتخاب‌شده برای validation
    استفاده کن؛ یک الگوی ثابت انتخاب کن و دو سیستم موازیِ بی‌دلیل نساز.
-   قراردادهای API نوع‌دار و مستند باشند.
-   خطاها ساختار استاندارد و پیام امن داشته باشند.
-   logging ساختاریافته و بدون اطلاعات خصوصی غیرضروری باشد.
-   health check و مدیریت graceful shutdown در صورت کاربرد پیاده‌سازی
    شود.
-   queryها پارامتری و امن باشند؛ از SQL injection جلوگیری کن.
-   عملیات طولانی اسکن فایل را از درخواست‌های سریع UI جدا کن؛ پیشرفت
    عملیات قابل گزارش باشد.
-   برای endpointهای پرتکرار، pagination و limit اجباری در نظر بگیر.
-   CORS را محدود و مشخص تنظیم کن؛ از wildcard بی‌دلیل استفاده نکن.
-   اگر API فقط روی localhost در دسترس است، binding، دسترسی شبکه و احراز
    هویت را صریح بررسی کن؛ localhost به‌تنهایی مرز امنیتی کامل نیست.
-   کلیدها و تنظیمات محیطی را از env یا سازوکار امن خارج از source code
    دریافت کن.
-   API و database نباید برای پخش عادی هر آهنگ، وابستگی شبکه‌ای غیرضروری
    ایجاد کنند.

## 9. امنیت Electron

امنیت Electron اجباری است:

-   `contextIsolation: true`.
-   `nodeIntegration: false`.
-   renderer sandbox را فعال نگه دار مگر دلیل مستند و بررسی‌شده‌ای برای
    استثنا وجود داشته باشد.
-   فقط APIهای ضروری و محدود را از Preload expose کن؛ هرگز کل
    `ipcRenderer` یا Node API را expose نکن.
-   sender و payload پیام‌های IPC را اعتبارسنجی کن.
-   navigation و `window.open` را محدود کن؛ محتوای ناشناس را داخل پنجره
    اصلی باز نکن.
-   از CSP مناسب استفاده کن.
-   لینک خارجی فقط با allowlist و از طریق مسیر امن سیستم باز شود.
-   مسیر فایل و ورودی کاربر را برای جلوگیری از path traversal اعتبارسنجی
    کن.
-   اطلاعات حساس را در log یا crash report درج نکن.
-   dependencyها را به‌روز و آسیب‌پذیری‌ها را بررسی کن.
-   برای production، DevTools و تنظیمات توسعه‌ای را مطابق نیاز محدود کن؛
    در development ابزارهای تشخیصی لازم باقی بمانند.

## 10. کارایی و پایداری

-   UI باید هنگام اسکن، جست‌وجو و بارگذاری کتابخانه responsive باقی
    بماند.
-   از queryهای N+1 و بارگذاری غیرضروری metadata جلوگیری کن.
-   داده‌های حجیم را یک‌باره به Renderer نفرست.
-   از virtual scrolling برای لیست‌های بزرگ استفاده کن.
-   cacheها اندازه و سیاست invalidation مشخص داشته باشند.
-   event listenerها، subscriptionها و timerها را به‌درستی پاک‌سازی کن.
-   از re-render غیرضروری Vue جلوگیری کن؛ ابتدا اندازه‌گیری، سپس
    بهینه‌سازی.
-   زمان startup، زمان اولین نمایش کتابخانه، زمان شروع پخش و مصرف حافظه
    را اندازه‌گیری کن.
-   برای عملیات async، cancellation و مدیریت race condition را در نظر
    بگیر.
-   خطای یک فایل نباید کل اسکن یا کتابخانه را از کار بیندازد.
-   خطاهای شبکه/DB را از خطاهای فایل و پخش جدا تشخیص بده.
-   هیچ بهینه‌سازی‌ای نباید صحت پخش یا تجربه کاربر را قربانی کند.
